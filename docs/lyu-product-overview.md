# Lyu & Lyu Desktop：一个可扩展的终端 Agent 产品

## 一句话

Lyu 是一套自有的 AI 编码 Agent 产品：终端形态 `lyu` 是完整的可交互编码代理，桌面形态 `Lyu.app` 是它的图形外壳，两端共享同一个引擎、同一份配置、同一套扩展。

## 产品定位

不是"又一个 AI 对话框"，而是**可扩展的 Agent 运行时**：

- 终端里 `lyu` 直接工作，不需要额外守护进程
- 桌面端通过同一引擎驱动会话，把 Agent 能力搬进图形界面
- 扩展是第一等公民：7 个自研扩展构成产品差异，而不是挂在核心上的插件

## 架构

```
┌─────────────────────┐        ┌──────────────────────┐
│  Lyu.app（桌面）     │        │  lyu（终端）          │
│  Electron 白标外壳   │        │  TUI + 交互模式        │
└──────────┬──────────┘        └──────────┬───────────┘
           │ spawn / RPC                  │
           └──────────────┬───────────────┘
                          ▼
              ┌───────────────────────┐
              │  引擎包 lyu-code       │
              │  vendored 上游发行版    │
              │  身份来自 piConfig      │
              └───────────┬───────────┘
                          │ 加载扩展包
                          ▼
              ┌───────────────────────┐
              │ @lyu/extensions       │
              │ 7 个扩展（自有）        │
              └───────────────────────┘
```

**关键设计：引擎与扩展拆成两个包。** 引擎运行时依赖的 4 个 host 模块，扩展必须以 `peerDependencies: "*"` 声明，否则会装出重复副本、绕过扩展加载器（引擎启动时会直接警告）。同一个 `package.json` 既当宿主又当扩展必然冲突 —— 这是拆包的直接动因，不是洁癖。

## 自研扩展（产品差异所在）

| 扩展 | 解决什么 |
| --- | --- |
| `memory` | 跨会话长期记忆，本地嵌入（24M 模型缓存在 agent 目录），不联外网 |
| `guard` | 危险操作前置拦截 + 审计日志 |
| `subagent` | 把独立任务派给子代理，过程不占主上下文 |
| `todo` | 分步计划维护，做完一步更新一步 |
| `stats` | 用量与成本统计 |
| `codegraph` | 代码结构索引与查询 |
| `plannotator-auto` | 自动代码评审、人工批注回传 |

**共同的设计约束**（写进代码，不靠自觉）：

- 任何 hook 永不打断会话 —— 但**失败必须说一声**。降级可以，静默降级不行
- 扩展里不许写死 `~/.pi`，一律走 `agentDir()` 解析
- 配置目录跟着产品走（`~/.lyu/agent`），项目目录 `.lyu/`，读的时候兼容老 `.pi/`

## 身份与配置：一个容易漏的坑

引擎的身份（产品名、配置目录名、环境变量名）全部来自包的 `piConfig`：

```json
{ "piConfig": { "name": "lyu", "configDir": ".lyu" } }
```

于是 `LYU_CODING_AGENT_DIR`、`~/.lyu/agent`、`lyu` 命令名全部自动派生 —— 品牌名只有一处来源，没有第二个地方需要同步。

**踩过的坑记在这里：** 字面量 grep 不到 ≠ 引擎不支持。`LYU_CODING_AGENT_DIR` 在 dist 里搜不到，因为它是由 `${APP_NAME.toUpperCase()}_CODING_AGENT_DIR` 在运行时拼出来的。差点为这个"不存在的 bug"动手改引擎。

## 引擎升级：vendored + 可回归的补丁层

引擎层不 fork 源码，而是**锁定上游发行版**（21M 自包含 dist，`vendor.piCLI` 声明版本），产品层完全自有。理由：上游修 bug 只需改一个版本号；一旦 fork，就要长期维护一个 72 万行的引擎。

上游有极少数地方把产品名写死了，改了品牌就必须打补丁。补丁遵循两条铁律：

1. **绝不硬编成 "Lyu"** —— 只许把「写死的 pi」换成「从 `APP_NAME` 派生」。`APP_NAME = "pi"` 时结果必须与上游逐字节一致，否则那不是改品牌而是分叉
2. **打不上就中止** —— 命中 0 次等于没打，装上去的东西会静默说谎，比装不上更糟

打完还逐个 `node --check` 体检。这条不是形式主义：曾有一次补丁把 import 注进了 27 个组件文件，其中一个本来就 import 了同名符号，变成重复声明、语法直接错，而它是包里没被引用的副本 —— 不体检就永远发现不了。

## 桌面端（Lyu.app）

Electron 白标构建，bundle id `sh.lyu.desktop`，自定义 About 面板，隐藏上游社区链接，关闭自动更新通道（否则会被上游安装包覆盖）。

两个只有踩过才知道的点：

- **打包顺序错了会白屏**：桌面端的 `build` 不构建前端 bundle，缺那一步打出来的 App 窗口是空的，而 electron-builder 对缺失的 `extraResources` 不报错，只静默拷一个空目录
- **Finder 启动拿不到 shell 的 PATH**：Electron 从 Dock 启动继承的是 launchd 的环境，所以需要主动 spawn 登录 shell 抓环境，否则找不到 CLI

桌面端与引擎的连接点目前有两处：CLI 命令解析（经环境变量可覆盖）和 Workflow tab（指向本地 `127.0.0.1:18789`，服务由 workflow 扩展在会话启动时拉起）。把这两处接成真正打通，是当前进行中的工作。

## 迁移工程：把用户从旧版无损搬到新版

一次真实的引擎大版本迁移（0.87.1 → 1.5.2），涉及：

- **配置迁移**：11 条扩展开关、模型/provider 定义、全局指令、项目信任记录
- **容易漏的一处**：项目信任是**按 agent 目录分开存的**。不种信任文件，扩展一个都不加载，而且**不报错** —— 用户会以为功能坏了，实际是静默跳过
- **工具撞名**：开发副本与打包版同时注册时，同名工具重复注册直接失败，需要去重
- **回退路径**：旧版本在 npm 上有发布，一行命令可回退；迁移前把旧目录整体备份而不是删除

验证一律走实测：`lyu --version`、真实模型调用返回、TUI 里 `[Extensions]` 逐个在列、pty 抓原始字节确认品牌字符串。不接受"看起来好了"。

## 已知限制（不藏）

- 第三方 TUI 扩展自带上游品牌，除非改它们或不用它们
- 版本检查目前指向上游发布源，待改为自有发布源
- 桌面端 daemon 数据目录仍是上游的，白标只到 UI 层
- vendored 发行版的 LICENSE/NOTICE 需要随包补齐（合规义务，不是可选项）
